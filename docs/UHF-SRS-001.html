1Introduction

1.1Purpose

This document specifies the software to be added to the RK3576 Android 14 source tree so that UHF RFID reader hardware becomes a first-class platform capability. Today the reader is reachable only by an application that claims the USB device directly and re-implements the wire protocol. That approach cannot be shared between applications, cannot survive the app being backgrounded, and forces every integrator to rediscover the protocol's undocumented behaviours.

The work specified here replaces that with a supported stack: one process owns the serial link, a system service arbitrates access and enforces permissions, and applications call a stable Java API. A distributable SDK lets third-party developers build against that API without access to the platform source.

1.2Scope

In scope. A vendor HAL process, a system server service, framework Manager and AIDL definitions, permission declarations, SELinux policy, device-tree and init integration, an SDK artifact with documentation and a reference application, and the test suite that gates all of it.

Out of scope. Reader firmware changes; the RFID tag commissioning workflow; any cloud or network sync of tag reads; industrial-design or enclosure work; support for the ISO 18000-6B protocol family, which this reader reports as unsupported.

Shall marks a binding requirement; should marks a strong recommendation; may marks an option. Each requirement carries a stable identifier (FR-ANT-03), a priority, and — critically — a verification status describing how well the underlying wire command is known.

Read this before estimating

The vendor manual R1 was not available on disk when this specification was drafted. Every command code marked Confirm is a strong inference from this reader family's shared command set, not a verified fact about this unit. The first task in Phase 1 is a documentation pass that resolves each of those into Verified or Documented. Requirements are written so that the API surface does not change when a code is corrected — only the constant behind it does.

2Overall description

2.1Product perspective

The reader is a serial peripheral that presents itself over USB through an FTDI FT232R bridge, enumerating as /dev/ttyUSB* under the in-tree ftdi_sio driver. It is a strictly command–response device: it transmits nothing until asked, with one exception — once placed in real-time mode it streams continuously, and that mode persists across power cycles.

The subsystem sits between that device and applications, and has four consumers: the OEM's own inventory application, third-party applications built against the SDK, platform diagnostics, and the factory test tooling that validates antennas at manufacture.

2.2Product functions

Grouped by the section that specifies them:

  • Session management — discover the reader, open and release it, arbitrate between competing applications, survive hot-unplug (§4.1).
  • Reader configuration — identity, firmware, address, serial link, regulatory region, frequency plan, RF power, antenna mask, antenna-check interlock (§4.2–4.6).
  • Tag acquisition — polled inventory, continuous streaming, and buffered inventory, each with its own latency and throughput profile (§4.7–4.9).
  • Tag manipulation — read and write all four memory banks, rewrite EPC, block write and erase, kill, lock, access-password management (§4.10–4.11).
  • Tag protection — read protection with and without EPC, TID-based protection, EAS alarm set and detect (§4.12–4.13).
  • Peripheral control — GPIO, relay outputs, buzzer, Wiegand output for door controllers (§4.15).
  • Diagnostics — antenna return loss, raw frame passthrough for field support (§4.16).

Measured — governs §6 performance requirements

Antenna switching, not the UART and not the RF, dominates the read rate. Dropping from four enabled ports to one is worth 2.5×. All fourteen tags were readable on port 1 alone, so the additional ports bought coverage rather than throughput. The API must therefore make the enabled-antenna set an explicit, per-session choice rather than a global default.

Scan time 0x25 has no effect in real-time mode. 100 ms and 300 ms stream at an identical rate; only the polled path honours it. The API must not present it as a streaming tuning knob.

A 900 reads/sec target is unreachable at 115200 baud. Tag frames measure ~18 bytes, so the UART ceiling is 11520 ÷ 18 ≈ 640 frames/sec before RF is even considered. Approaching 900 requires both a baud-rate increase (§4.3) and a far larger tag population — at fourteen tags the reader is bound by per-round overhead, not by tag count.

2.5Assumptions and dependencies

  • The reader remains an FTDI-bridged serial device. If a future unit exposes a native USB CDC or a direct UART connection, only the HAL's transport layer changes — §4 and §5 are transport-agnostic by design.
  • ftdi_sio is built into the RK3576 kernel and binds the device automatically.
  • The build is userdebug during development. Requirements that depend on adb root are development aids only and are called out where they appear.
  • Antenna port 3 on the current unit is faulty and must be excluded from any default mask (see R4).

3.2Why the HAL is a separate process

The serial device is vendor hardware. Putting the protocol implementation in system_server would mean a system-partition process holding a vendor device node open, which violates Treble layering and makes the device node's SELinux label awkward to express. It would also mean a protocol bug — a runaway resync loop, a blocking read without a timeout — could take down system_server and with it the device.

A separate vendor process isolates that risk: if the HAL dies, init restarts it, UhfService observes the binder death, and clients receive a state callback. Nothing else on the device is affected.

Phased alternative

For Phase 1 bring-up only, UhfService may talk to the tty directly through JNI, skipping the HAL. This shortens the first integration considerably and lets the API surface be validated early. It is explicitly a temporary arrangement: BLD-09 requires the HAL split before the subsystem ships.

3.3The streaming data path

This is the performance-critical path and the one most easily got wrong. At 130 reads/sec — and far more if the baud rate rises — a design that crosses a process boundary once per tag will spend more time in IPC than in RF.

reader ──serial──▶ HAL pump thread
                     │  parse frames, drop CRC failures, resync
                     │  accumulate into a batch buffer
                     ▼
                   batch flush  ── every 50 ms OR 64 tags, whichever first
                     │
                     ▼  oneway Binder, one call per batch
                   UhfService dispatch thread
                     │  fan out to registered sessions
                     ▼  oneway Binder, one call per batch per client
                   UhfManager
                     │  marshal onto the client's Executor
                     ▼
                   app: onTagsRead(List<TagRead>)

The batch window is the single tuning parameter. At 50 ms it yields 20 Binder transactions per second regardless of read rate, while adding at most 50 ms of latency to a tag sighting.

Measured — a mistake worth not repeating

The reference application originally posted a UI refresh per tag read. At 130 reads/sec this saturated the main thread and froze the display entirely, while the reader itself was keeping up perfectly. The same failure mode is available one layer down: a per-tag Binder call. Batching is a requirement, not an optimisation.

Why FR-LC-09 is P1 while FR-LC-08 is P2

FR-LC-08 bundles antenna mask, power and region together as one general "restore prior config" feature, deferrable to P2. But region is not like the other two: an antenna mask or power level reverting to default after a crash is a throughput regression; a region reverting to default is the reader transmitting on the wrong regulatory band, and FR-FRQ-04 only logs a region change when a caller makes one deliberately — a crash-triggered reset generates no log entry at all. Shipping FR-LC-08 at P2 without FR-LC-09 would mean a HAL crash can silently move the device out of its licensed band, undetected, for as long as it takes P2 to land. Region gets its own, higher-priority, non-reader-dependent persistence path instead of waiting on the general mechanism.

Why FR-LC-05 exists

Real-time mode is stored in the reader's non-volatile configuration and survives a power cycle (R1 §8.4.23). A device that was streaming when it was switched off is still streaming when it comes back. Without an unconditional reset at boot, the first client to open the port meets a flood of unsolicited tag frames, and every command reply it sends arrives interleaved with them. During bring-up this presented as a reader that "answered garbage" and cost significant time to diagnose.

Why FR-LNK-06 is load-bearing

In real-time mode the reader floods the port with 0xEE tag frames. Those frames have valid CRCs and a success status, so a receiver that accepts "the first structurally valid frame" as a command reply will accept a tag report instead. Every subsequent configuration step then silently applies to nothing. Matching reCmd is the only reliable discriminator.

Dependency for the throughput goal

FR-LNK-02 is the gate on any read rate above ~640 frames/sec. Whether this reader accepts 230400 or 460800 is not yet established — R2 documents values only up to 115200 (0x06). Resolving this is tracked as OI-03.

The interlock. Command 0x3F is rejected with status 0xF9 whenever antenna check 0x66 is enabled. The working order is: check off, write mask, check on. Without this the mask write appears to fail for no reason.

The abort. Since port 3 on the current unit is faulty, any default mask that includes it produces a reader that appears completely dead.

Why FR-STR-13 exists

NFR-C-01 already establishes that the reader accepts one command per cycle and the HAL serialises all transactions on a single thread. Rev A stated the consequence for configuration writes (FR-STR-08) but not for the other command families that share the same constraint — a caller starting a buffered inventory or a tag write while a stream is running would either corrupt both exchanges or hang behind the pump thread with no documented behaviour either way. Rather than three near-duplicate requirements in §4.9–4.13, this generalises FR-STR-08's rule to any non-streaming call and those sections reference it instead of restating it (see FR-BUF-07).

Measured — the basis for FR-STR-10

Entering real-time mode costs five to ten seconds of command round trips before the first tag arrives. A rate computed from the start call divides by that dead time and understates the true rate by roughly half — a reference implementation reported 24 reads/sec on a link that was actually delivering 50. Timing must begin at the first delivered read.

A second trap: counters that accumulate across runs. Clearing must reset the time base as well as the totals, or successive measurements drift upward.

8.2Device node ownership

The node is crw------- root root today, which is why the reference application had to claim the USB device from userspace and detach ftdi_sio. The HAL needs the node instead.

Rev B — the shared-file trap

There is no per-board ueventd.rk3576.rc. Every Rockchip product that inherits device/rockchip/common/device.mk — rk3576_u, rk3576_ebook, and every other Rockchip board in this tree — gets its ueventd rules from one shared file, device/rockchip/common/rootdir/ueventd.rockchip.rc, copied by rootdir.mk to /vendor/etc/ueventd.rc. Writing the reader's rule body directly into that file would apply it fleet-wide.

The fix is the pattern the file already uses for exactly this problem: line 1 of ueventd.rockchip.rc is import /vendor/etc/ueventd.car.rc — an unconditional import of a fragment that only car products copy into the image. On every other board the import target is simply absent and the import is a no-op; this is proven safe by the shipped default configuration, which is a non-car product and boots fine today. The reader's rule follows the same shape, one level down (ueventd.car.rc itself imports ueventd.rvcam.rc the same way).

# device/rockchip/common/rootdir/ueventd.rockchip.rc  (edit — one line, applies to every board)

import /vendor/etc/ueventd.uhf.rc

Constraint on the ueventd rule

Even scoped to this product, /dev/ttyUSB* still matches every USB serial device on this board, including a debug adapter someone plugs in for bring-up. NFR-S-02 requires narrowing this — by a DEVPATH match on the reader's vendor and product ID, or a udev-style symlink — before the rule ships as anything but a Phase 1 development convenience. Tracked as OI-05.
